🔧 How AWS Services Work Together

1. Network Layer (AWS Default VPC) 
AWS Default VPC (172.31.0.0/16)
  ├─ Internet Gateway - Pre-configured
  ├─ Subnets (172.31.*.0/20) - Multi-AZ subnets
  ├─ Route Table - Routes traffic 0.0.0.0/0 → IGW
  └─ Elastic IP - Assigned to EC2 for static public access

Advantage: Free tier friendly, no custom VPC setup needed
Result: User can reach EC2 via public IP through default infrastructure
2. Compute Layer (AWS EC2 + EBS) 
EC2 Instance (t3.micro)
  ├─ OS: Ubuntu 22.04 LTS
  ├─ Root Block Device: 30GB EBS
  ├─ Security Group: Allow SSH(22), HTTP(80), HTTPS(443), K8s(6443, 10250, 30000-32767)
  └─ Docker daemon + kubelet running

Result: Container runtime ready to run K8s
3. Security Layer (AWS IAM + Security Groups) 
Security Group (Firewall)
  ├─ Inbound: SSH :22 (your IP only)
  ├─ Inbound: HTTP :80 (0.0.0.0/0)
  ├─ Inbound: HTTPS :443 (0.0.0.0/0)
  ├─ Inbound: K8s API :6443 (VPC internal)
  ├─ Inbound: NodePort :30000-32767 (0.0.0.0/0)
  └─ Outbound: All (to reach Docker Hub, updates)

Result: Only desired traffic reaches the instance

Detailed Flow:
  1. User Request → GET http://<ec2-ip>:<nodeport>/api/tasks
  2. K8s Service → Routes to Nginx frontend pod (load balanced)
  3. Nginx Proxy → /api/* → Forwards to backend pod (http://backend:5000)
  4. Flask API → Processes request, connects to PostgreSQL
  5. Database → Executes query, returns task data
  6. Response Path → Flask → Nginx → K8s Service → Client Browser

📈 Scalability Demonstration

🟢 Normal Traffic
  • Pods: 2 replicas
  • CPU: ~10%
  • Memory: ~50MB
  • Response Time: <100ms
🔴 High Traffic (Load Test)
  • Pods: 5 replicas (HPA triggered)
  • CPU: ~80%
  • Memory: ~200MB
  • Response Time: <500ms
Auto-Scaling Rules: When average CPU > 70% OR memory > 80%, scale up to 5 pods. When load decreases, scale down to 2 pods.

⏱️ Request Lifecycle - Detailed Timeline

1. User Action (Browser) 
fetch('/api/tasks')  // Request from browser
⬇️ <50ms via HTTP>
2. Kubernetes Service (Load Balancing)
  • K8s service receives request on port 80/nodeport
  • Looks up available pods (could be 2-5 replicas)
  • Selects pod via round-robin load balancing
  • Forwards to pod IP:port
⬇️ <1ms (local network)>
3. Nginx Frontend (HTTP Proxy) 
Request: GET /api/tasks
Nginx nginx.conf sees: location /api/ { proxy_pass http://backend:5000 }
Forwards: GET http://backend:5000/api/tasks
⬇️ <1ms (K8s DNS lookup)>
4. Flask Backend (Application Logic) 
@app.route('/api/tasks', methods=['GET'])
def get_tasks():
    conn = get_db_connection()  # Connect to PostgreSQL
    cur = conn.cursor()
    cur.execute('SELECT * FROM tasks')
    tasks = cur.fetchall()
    return jsonify(tasks)
⬇️ <5-50ms>
5. PostgreSQL Database (Query Execution)
  • Execute SQL: SELECT * FROM tasks ORDER BY created_at DESC
  • Fetch results from persistent volume
  • Return JSON-serialized data
⬇️ <Response Path>
6. Response to Browser 
HTTP/1.1 200 OK
Content-Type: application/json
[{"id": 1, "title": "Buy milk", "created_at": "2024-01-15"}]
Total Request Time: ~10-100ms (depending on database query complexity)
  • Network latency: ~1-5ms
  • Nginx processing: <1ms
  • Flask processing: ~1-5ms
  • Database query: ~5-50ms
  • Serialization & network: ~1-5ms

🔄 DevOps Workflow - From Code to Production

1. Developer writes code 
git commit -m "feat: Add task API"
git push origin main
⬇️
2. GitHub webhook triggers Jenkins 
GitHub Webhook: https://jenkins.local/github-webhook/
Jenkins receives: "Code pushed!"
Pipeline starts automatically
⬇️
3. Jenkins builds Docker image 
docker build -t user/app:v1.2.0 .
docker push user/app:v1.2.0
Image tagged with build number (v1.2.0)
⬇️
4. Jenkins deploys with Helm 
helm upgrade --install task-app ./helm-charts/task-app \
  --set image.tag=v1.2.0
Helm updates K8s manifests with new image version
⬇️
5. Kubernetes orchestrates rollout 
K8s sees: "New image version detected"
Rolling update: Launches new pods with v1.2.0
Waits for health checks to pass
Removes old pods once healthy
⬇️
6. Application is live! 
Old pods:  TERMINATED (graceful shutdown)
New pods:  RUNNING with v1.2.0
Users see: Latest code immediately
Metrics show: Zero downtime deployment
If deployment fails:
  • Health checks detect new pods are unhealthy
  • Jenkins automatically: helm rollback
  • Old pods restore (previous working version)
  • Users never see broken version
  • Alert sent to team for investigation

⚠️ Failure Scenarios & Recovery

Pod Crash: K8s detects failed readiness probe → restarts pod automatically within 10-30 seconds
High Traffic Spike: Metrics exceed threshold → HPA triggers → new pods scheduled → traffic distributed across replicas
Image Build Failure: Jenkins detects failed build → stops deployment → keeps running old version → alerts sent
Node Failure: EC2 dies → pods evicted → rescheduled on remaining nodes (with 2+ replicas)
